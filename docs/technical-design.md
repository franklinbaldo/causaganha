# Technical Design Document (TDD)

## Architecture Overview

CausaGanha V2 is designed as a modular, pipeline-driven system. The architecture cleanly separates concerns into layers and components, enabling easier maintenance and testing. All core operations (data fetch, analysis, DB queries) are implemented with asynchronous I/O to maximize throughput (using Python’s asyncio). Key architecture principles include: dependency injection (passing in external services like the database or API client to pipeline functions for decoupling) and a clear data flow through discrete pipeline stages.

## System Layers and Components

The system can be viewed in three layers:

1.  **CLI Layer (causaganha CLI)** – The user-facing entry point. The CLI parses commands and orchestrates high-level operations. For example, running `causaganha pipeline` will sequentially trigger the collect, archive, analyze, and score steps. The CLI is built with Typer or Click (noting the code structure), and provides subcommands for each pipeline stage and utilities (e.g. database init, status).

2.  **Pipeline Layer (src/causaganha/pipeline/)** – The core orchestration logic. There are separate modules for each major step: `collect`, `archive`, `analyze`, `score`. Each pipeline function coordinates between the data layer and relevant services. For instance, `collect` fetches case metadata via the API client and saves it to the database; `archive` takes pending items from DB, downloads PDFs via the document service, and uploads them via the archive service, marking them archived in DB; `analyze` uses the analyzer (LLM) to process each document’s text and stores the extracted results; `score` computes or updates OpenSkill ratings based on analyzed outcomes. The pipeline ensures that each step enriches the data and updates the state (often in the DuckDB) before moving on. All pipeline steps are asynchronous (e.g. can download or analyze multiple documents in parallel).

3.  **Services & Storage Layer** – A collection of components that provide external interfacing and data persistence:

    *   **External API Client (causaganha.api.client)** – Handles communication with the PJe API for fetching case metadata (intimações). This is an async HTTP client (likely built on httpx) that abstracts endpoint calls and pagination. It converts JSON responses into Python models (using Pydantic) for downstream use.
    *   **Document Service (causaganha.services.document)** – Manages downloading PDF files of decisions. It knows how to construct download URLs or use the links provided by the API, retrieve the PDF, and store it temporarily. This service may also handle any necessary PDF parsing or text extraction if needed for analysis.
    *   **Archive Service (causaganha.services.archive)** – Responsible for uploading documents to the Internet Archive (IA) or storing them locally as a fallback. It uses the IA API (via the internetarchive Python library) to create or update the single master IA item that holds all PDFs. This service ensures each PDF is named and placed correctly (e.g. under a path for its court) and logs the upload status. If IA credentials are not configured, it will save files to a local directory instead (to avoid data loss).
    *   **Analyzer (causaganha.analysis.analyzer)** – Encapsulates the AI logic for decision analysis. It sends document text to an LLM (through the Pydantic-AI abstraction, possibly using an API key for Google Gemini models) and parses the model’s structured output. This component defines the prompts and expected schema (e.g. a Pydantic model for “DecisionAnalysis” that includes fields like winner, loser, involved lawyers, etc.). The analyzer ensures consistent output and may include post-processing hooks (like PII anonymization) on the model’s response.
    *   **Repository/Storage (causaganha.storage.\*)** – Abstraction over the DuckDB database using the Ibis framework. This handles all database operations: establishing a DuckDB connection, creating tables (schema definitions for intimations, decisions, ratings, etc.), and executing queries/inserts. By using Ibis, the code can write high-level Pythonic expressions that translate to efficient SQL for DuckDB. The repository provides functions like `store_intimation(metadata)`, `mark_archived(id)`, `fetch_unanalyzed()` or `update_rating(lawyer_id, new_rating)`, encapsulating SQL details. The DuckDB database itself is a local file (e.g. `data/causaganha.duckdb`), and contains both raw data and derived tables. This design allows analytical queries via SQL and also integration with dbt for transformations and testing (a future migration to manage schema via dbt-duckdb is planned).

All these components interact in a controlled flow. The dependency injection principle is seen, for example, in the pipeline passing a database connection or repository instance into the analyzer or archive service, rather than those components initiating their own connections. This makes it easier to unit test components in isolation by swapping real services for mocks.

## Data Flow

The end-to-end data flow can be summarized as follows, mirroring the pipeline stages:

*   **Collection Stage:** The process starts when the user invokes `collect` (or the pipeline as a whole). The collect module calls the PJe API to retrieve all new case intimations (entries) in the specified date range for a given court. The API client handles pagination and returns a list of case metadata records (each includes an ID, case number, involved parties, lawyers, and a link or reference to the decision document). These records are inserted into the DuckDB database (in an `intimations` table) with a status indicating they are collected but not yet archived.

*   **Archive Stage:** Next, the archive step checks the DB for collected intimations that have not yet been archived. For each, it uses the Document Service to download the PDF of the decision (using the URL or identifier from the metadata). Once downloaded, it uses the Archive Service to upload that PDF to the Internet Archive master collection. On success, the database record for that decision is updated (e.g. an `archived_at` timestamp or status set to archived). This stage ensures a permanent copy is stored externally and marks the item ready for analysis. (If the user runs with `--dry-run`, the archive step can be tested without actual IA upload, storing files locally instead.)

*   **Analysis Stage:** The analyze step finds archived decisions that haven’t been analyzed yet (e.g. those with PDFs downloaded). For each, the Analyzer (LLM) is invoked – it reads the PDF (could convert to text) and applies a prompt to extract structured info like who won the case, which lawyers represented each side, etc. The LLM’s structured output (e.g. a JSON parsed by Pydantic) is then stored in the database (in an `analysis_results` table, keyed by the case or intimation ID). Each record might include fields like `winner_lawyer_id`, `loser_lawyer_id`, case outcome, and any confidence metrics. The system marks the case as analyzed (with a timestamp and any error if analysis failed). This yields a growing repository of case outcomes and associated lawyers, all linked back to the original case entries.

*   **Scoring Stage:** Finally, the score step takes the latest analysis results and updates the lawyer ratings. It uses the OpenSkill algorithm (via the `openskill.py` module) to rate lawyers similar to how Elo or TrueSkill rates players. For each case outcome: the winning lawyer(s) gain points and the losing lawyer(s) lose points, with adjustments for their prior ratings and uncertainty. The OpenSkill model used (Plackett-Luce model with μ/σ) is configured in the settings (with default μ=25, σ≈8.33). The scoring module updates a ratings table in DuckDB, which stores each lawyer’s current rating (mu, sigma) and maybe a history of matchups in a `partidas` table. After processing, lawyers involved in the new cases will have their ratings adjusted. This step produces the up-to-date leaderboard of lawyer performance.

The data flow is cyclical in that new data can continuously enter via collection (new cases each day), and subsequent stages process it. There is also a continuity mechanism (perhaps the `continuity.py`) to handle interruptions or re-running stages safely – e.g., to avoid reprocessing the same case twice or to resume after a failure.

Throughout the pipeline, each stage records its progress in the database (e.g., flags for archived/analyzed) and can be re-run idempotently where possible. The modular design means one can also run stages independently (for example, re-run analyze on items if the AI model is improved, or run only collect daily and archive later in bulk).

## Key Technical Decisions & Rationale

*   **Use of DuckDB + Ibis for Storage:** DuckDB was chosen as the analytical database for its high performance on columnar data and ability to run complex queries efficiently in-process. The team moved away from Pandas in V1 due to memory and speed issues. By integrating DuckDB, queries (like joining decisions to lawyer info or computing aggregates) can run 10-100× faster with low memory overhead. Ibis provides a layer of abstraction, making the code more maintainable as the schema evolves (no hand-written SQL scattered in code) and enabling integration with dbt for schema management. This decision significantly improves scalability and maintainability of the data layer.

*   **Switch from Web Scraping to Official API:** V1 relied on scraping court diary PDFs, which was brittle and limited to one court. V2’s design to use the PJe Comunica API is a critical change. The API provides structured JSON data with lawyer names, case numbers, etc., solving the “missing metadata” issue (no need to parse PDFs for names). This massively improves data quality and paves the way to integrate many courts (since most Brazilian courts use the PJe system). The trade-off is handling API-specific constraints like geo-blocking and needing to adapt to API changes, but overall it’s a more robust data source.

*   **OpenSkill for Rating:** The project adopted the `openskill.py` library (LGPL) as the core rating engine to rank lawyers. OpenSkill was chosen over alternatives (like TrueSkill) due to its patent-free license and similar capabilities. This decision allows CausaGanha to have a transparent and adjustable rating system (parameters like beta, tau can be tuned in config) without legal risk. The rating calculation is done in the final pipeline stage to separate concerns (analysis determines outcomes; scoring concerns only the abstract “who won/lost” data). Each case is treated like a “match” between two “teams” of lawyers for rating purposes. The design keeps the rating logic encapsulated in one module, which is tested independently (with unit tests ensuring parity with expected Elo-like behavior).

*   **Internet Archive as Distribution Channel:** Instead of building a custom web portal for distributing data, the team uses the Internet Archive (IA) to openly publish the collected data and backups. This decision leverages IA’s infrastructure (redundancy, public access, even torrent downloads) for free open data hosting. The “single master item” approach – where all court PDFs and metadata are added under one IA identifier – simplifies management. It means users can find everything in one place, and the project can update a single record for new data. The technical design includes maintaining a local `job_queue` table that tracks what has been uploaded to IA and a mechanism to add incremental metadata (for example, a JSON summary of analyses) to the IA item as new information becomes available. Using IA imposes a constraint (upload speeds, needing API keys), but it aligns with the goal of maximum transparency.

*   **FastAPI for Future Services:** While the core is CLI-based, the design anticipates a future where either a monitoring dashboard or an API might run as a web service on top of the data. The repository mentions possibly using FastAPI for a simple dashboard backend. This would allow real-time queries of the DuckDB (e.g. via HTTP requests) and potentially serving a web UI. The architecture for now remains a “modular monolith” (everything in one codebase), but the boundaries (CLI vs services vs storage) mean it could be deployed as separate processes if needed (e.g. a background worker for pipeline, a web server for dashboard). The decision to keep things in one repo with clear modules means lower complexity until scaling demands otherwise.

Overall, the technical architecture emphasizes clear separation of concerns, testability, and scalability. Each component (API client, analyzer, etc.) has a well-defined interface, making it possible to replace or upgrade components (for example, swapping out the LLM model provider, or adding support for another external API) with minimal impact on the rest of the system. This foundation is crucial as CausaGanha moves into its next phases, where multi-tribunal support and new features will be added on top of this core architecture.
