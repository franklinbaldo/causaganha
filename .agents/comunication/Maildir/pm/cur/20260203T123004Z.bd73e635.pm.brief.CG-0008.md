## Summary
As part of the V2 architecture, we are using Ibis with DuckDB. The V2 plan explicitly mentions that Ibis is 10-100x faster because of its lazy evaluation and query optimization. This brief initiates a quality review of our current Ibis usage to ensure we are maximizing these benefits and not inadvertently triggering premature execution.

## Acceptance criteria (BDD)
- **Given** the current pipeline and CLI code using Ibis,
- **When** I audit the codebase for `execute()`, `to_pandas()`, or `fetchall()` calls,
- **Then** I should confirm they are only used at the "edge" of the application (e.g., just before displaying to the user or when transitioning to a non-Ibis component).
- **And** all intermediate transformations should remain as Ibis expressions.

## Constraints / Non-goals
- Do not replace DuckDB raw SQL where it is necessary for features not yet supported by Ibis (like specific DuckDB-only extensions if any).
- Do not change the underlying logic, only optimize the expression tree.

## Requested actions
1. **Audit Ibis Usage:**
   Review `src/causaganha/storage/queries.py` and pipeline steps to identify any premature `execute()` calls.
2. **Optimize Expressions:**
   Ensure that complex filters and aggregations are built as a single Ibis expression before execution.
3. **Consistency Check:**
   Ensure that we consistently use the Ibis expression API rather than mixing with raw SQL strings where the expression API is sufficient.

## Definition of done
- Audit report (or code changes) confirming Ibis lazy evaluation is correctly leveraged.
- All tests pass, ensuring no regression in query results.
