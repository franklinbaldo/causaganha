## Summary
The V2 architecture aims to transition from legacy DJEN ZIP scraping to the modern PJe Communications API. While a `PJeAPIClient` exists in `src/causaganha/clients/pje.py`, the V2 pipeline collector (`src/causaganha/pipeline/collect.py`) is still using the proxy to download legacy ZIPs. This brief initiates the transition to the JSON-based PJe API.

## Acceptance criteria (BDD)
- **Given** the `PJeAPIClient` is available in the codebase,
- **When** I refactor `src/causaganha/pipeline/collect.py` to use `PJeAPIClient.get_intimations_by_court()`,
- **Then** the metadata collection should fetch structured JSON instead of downloading and extracting ZIP files.
- **And** it should correctly handle pagination using the client's built-in logic.
- **And** all unit tests in `tests/unit/test_pje_client.py` must pass.

## Constraints / Non-goals
- Ensure `PJeAPIClient` respects `settings.PJE_API_URL`.
- Maintain compatibility with the current `store_intimations` logic in DuckDB.
- Do not remove the legacy `scripts/pipeline/collect.py` yet as it is still used for backfilling historical ZIPs.

## Requested actions
1. **Refactor V2 Collector:**
   Update `src/causaganha/pipeline/collect.py` to use `PJeAPIClient`.
2. **Configuration Alignment:**
   Ensure `PJeAPIClient` initialization uses `settings.PJE_API_URL`.
3. **Robustness:**
   Ensure the refactored collector handles the transition from `SimpleNamespace` (used currently) to the `Intimation` Pydantic model correctly when calling `store_intimations`.

## Definition of done
- V2 collection pipeline uses the PJe Communications API.
- Successful end-to-end collection of metadata for at least one court (e.g., TJRO) into DuckDB.
- Tests pass.
