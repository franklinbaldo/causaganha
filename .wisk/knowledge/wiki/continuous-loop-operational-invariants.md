# Continuous-loop operational invariants

## Summary

The continuous CausaGanha loop is most reliable when Wisk owns orchestration and each session treats current repository/GitHub state as evidence rather than assuming that the issue backlog is the whole work queue. Recent Experience runs repeatedly found useful, bounded work after the open issue queue was blocked: a shipped CLI without tests exposed a real validation defect (#1265), an entirely unused legacy inventory implementation was removed (#1267), and a persistence defect in the Wisk bootstrap path was found and repaired (#1270/#1271).

Wisk state has one canonical repository namespace: `.wisk/`. Versionable Experience, Wiki, Skill and local consumer knowledge belong beneath `.wisk/knowledge/`. During the package rename, #1270/#1271 temporarily used a tracked `.wisk -> .wikiskill` symlink to prevent state loss; #1274 later migrated the entire historical tree into `.wisk/` and removed the old namespace. The symlink is therefore useful migration evidence, not a current invariant and not a pattern to recreate.

Cross-session PR continuation should remain explicit through Wisk handoffs. A run that leaves CI or merge work pending records a Handoff; the continuing session first reconstructs the factual repository/GitHub state, then acts on the still-valid remainder and archives the Handoff only after resolution. A stale handoff instruction is never stronger evidence than the repository state observed on resume.

A green PR is not always immediately mergeable: GitHub can enforce a required status check (e.g. an app-provided "GitGuardian Security Checks" repository rule) that only reports against a head commit once something re-triggers it, independent of whether the repo's own CI workflow already passed on that same commit. Calling the merge API against such a PR fails with an HTTP 405 "Repository rule violations" naming the missing required check, even when `pull_request_read`'s own status view shows nothing blocking (a stale head can also leave the PR `mergeable_state: "behind"` its now-advanced base). The fix in both cases is the same action: update the PR branch (merge the current base into the head, e.g. via `update_pull_request_branch`), wait for the full required-check suite to report on the new head, then merge — do not conclude the PR is stuck or hand it back as an unresolved handoff without trying this first. This also matters when two independent loop rounds race on the same Handoff: one round's PR can sit open and merge-blocked for an extended period for exactly this reason, not because of any real conflict or review requirement, so a resuming round should check for and finish an already-open PR against a stale handoff rather than opening a duplicate.

A RunOutcome's `next_move` field is a legitimate work source in its own right, not just a courtesy note. Run 20260907T184502Z's outcome deferred two low-priority leads surfaced by an unrelated bugfix audit (a blind `except Exception` in `archive.py`, and `CircuitBreaker.is_open` reading a raw state field instead of its own class's dynamic `state` property). Run 20260907T192551Z investigated both with no new GitHub signal to go on (no owner-filed issue, no open PR, the 17-issue backlog still blocked): one was ruled out as already-correct (ruff's `BLE001` intentionally exempts handlers that call a `*.exception(...)` logger), the other was confirmed real and fixed with a dedicated RED→GREEN test (PR #1289, squash commit `b383135` — a sync-only caller reusing one long-lived `CircuitBreaker` across a whole run could never recover once it tripped open, because it only ever read the property that skipped the class's own time-based half-open promotion). When the issue backlog is exhausted and no handoff is pending, re-reading the most recent RunOutcome's `next_move` for an unresolved lead is cheaper and better-grounded than starting a fresh audit from scratch.

Three same-day bugs in `circuit_breaker.py` (`c352943`, `b383135`, and `#1293`) share one root cause worth naming as its own pattern: the class serves both a sync-only caller (`ia_s3.py`, which checks `is_open` then calls `record_success()`/`record_failure()` directly) and async callers (`archive.py`, `engine.py`, `drain.py`, which drive every state transition through `allow_request()`). Each bug involved a transition that one calling convention exercises and the other does not — `is_open` reading a stale raw field the async path never left stale (`b383135`), and `record_failure()`'s reopen-with-doubled-timeout branch only firing when `allow_request()` had already set `_probing` (`#1293`, found this round by re-reading the module against `ia_s3.py`'s actual usage rather than in isolation). A class shared between a sync and an async calling convention should be audited against *both* conventions explicitly, not just the async happy path that most of its tests exercise.

A fresh container checkout needs `wisk init .` before `wisk start` will select any SessionType. `.wisk/knowledge`'s managed bootstrap surface (`SessionType`/`RunSpec`/`CadencePolicy` records under `knowledge/system/`, plus `manifest.json` and `specs/`) is deliberately gitignored (`.wisk/.gitignore`) so it can be upgraded independently of the versioned consumer state (`experiences/`, `wiki/`, `skills/`, `local/`), but that means it does not exist at all right after a fresh `git clone` and `wisk start` fails with a bare `no-eligible-session`/empty `candidates: []` that gives no hint the fix is `wisk init .` (per `.claude/hourly-loop.md`). Two consecutive rounds (`20260907T222723Z`, `20260908T002654Z`) independently paid the full diagnosis cost for this in the same day; a future round hitting `no-eligible-session` with `candidates: []` should check for a missing `.wisk/knowledge/system/` directory first, before assuming the issue/handoff queue itself is exhausted.

`reset_manifest` (`src/djen_backup/service.py`, backing the `djen-backup reset` CLI command) is a second confirmed instance of a hazard worth naming on its own: a codebase that treats one field as the sole canonical status source (CLAUDE.md already states this for `djen_raw` vs. the derived `djen_status`, and `engine.py`'s check-priority builder enforces it at `engine.py:417-422`) must audit *every* function that clears or mutates the derived/mirrored fields, not just the ones an author happens to think of. `reset_manifest` cleared `ia_status`/`djen_status`/`updated_at` — exactly what its own docstring promised — but left `djen_raw` untouched, so `interpret_djen_raw()` re-derived the same terminal verdict the reset was supposed to clear, making the CLI command a silent no-op for exactly the entries an operator would run it against (fixed in PR #1297, squash `53cfe59`, with previously-zero test coverage for the function). The generalizable lesson: whenever a module names one field the canonical source of truth over a derived one, that invariant needs a positive test on every code path that resets/clears state, not just the read paths.

A shared domain exception needs auditing against every call site that can raise it, not just the one a change happens to touch — a distinct but structurally related hazard to the sync/async dual-calling-convention pattern above (both involve one abstraction with multiple independent consumers). `DJENRateLimitedError` is defined once, in `djen.py`, and raised by `get_caderno_url` for HTTP 403 (CloudFront/WAF block) — per CLAUDE.md's "never treat 403 as absent" rule, it exists precisely so callers treat a 403 as transient and retry rather than as a failure or an absence. `engine.py`'s `_classify_djen_status` and `probe.py` both already caught it explicitly. `drain.py`'s `_drain_one` (the newer batched upload-only drain mode) did not: its except clauses covered `DJENNotFoundError` and `(httpx.HTTPError, httpx.RequestError)`, but `DJENRateLimitedError` is a bare `Exception` subclass, not an `httpx` error, so a 403 propagated uncaught out of `_drain_one` and then out of `_drain_worker`'s `while True` loop, permanently killing that worker task for the rest of the run — exactly during the rate-limit bursts the exception exists to signal. Fixed with a RED (mocked 403, confirmed the exception propagated) → GREEN (added the missing `except` clause, matching the existing skip pattern) test in PR #1305. The generalizable check: when a module defines a domain exception for a shared client function, grep every call site of that function for a matching `except` clause before assuming an existing catch elsewhere means the exception is universally handled.

A human-facing architecture doc can drift from the codebase in the same way code itself can, and the failure mode is worse: it presents nonexistent files and functions as canonical guidance, not a stale claim about behavior. `FRONTEND.md`'s "Four tiers of state" (Tier 0) and "Dashboard queries with meta.json polling" sections documented `fetchAllData()`/`deriveData()`/`useDashboardWithPolling()` (the last from a `useDashboard.svelte.ts` file) and a `loadBuildTimeData()` helper (from a `buildTimeData.ts` file) as the current, working build-time-seed-plus-live-refresh architecture — complete with code samples attributed to real files (`[tribunal].astro`, `TribunalDetail.svelte`). Neither `useDashboard.svelte.ts` nor `buildTimeData.ts` exists anywhere in the repository (confirmed with `ls`/`grep`), and the two real files the samples were attributed to were independently verified to already use a different, current pattern (`loadContract()`/`readJson()` directly in `.astro` frontmatter, per CLAUDE.md's "Manifest query contracts"). The underlying `fetchAllData`/`deriveData` functions did still exist in `fetchData.ts` and type-checked cleanly, which is what let the doc's claim survive unnoticed — a stale reference to code that still compiles is much harder to catch by inspection than one that would fail to build. Fixed by deleting the dead exports (keeping `fetchWithRetry`, which is genuinely used) and rewriting every affected `FRONTEND.md` section with examples drawn from real, grep-verified call sites, landed as PR #1307. The generalizable check: before trusting or extending a claim in a project's own architecture doc — not just a wiki/knowledge entry about the loop itself — verify that every file and function it names actually exists and is called from where the doc says it is; a doc section can be "current" prose describing an abandoned or never-built subsystem for a long time before anyone reads it closely enough to check.

## Context & Scope

These rules apply to unattended or periodically invoked CausaGanha work sessions. They do not authorize speculative features when current issues are blocked, nor do they turn coverage/dead-code scans into a mandatory ritual. They describe a proven fallback: prefer independently verifiable repository improvements over manufacturing work merely to keep the loop busy.

The issue backlog remains important context, but it is a queue of known opportunities rather than a completeness claim about all possible useful work. Before acting on cached blocker descriptions, refresh the relevant GitHub/environment facts when staleness could change the decision.
