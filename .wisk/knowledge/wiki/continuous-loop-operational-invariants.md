# Continuous-loop operational invariants

## Summary

The continuous CausaGanha loop is most reliable when Wisk owns orchestration and each session treats current repository/GitHub state as evidence rather than assuming that the issue backlog is the whole work queue. Recent Experience runs repeatedly found useful, bounded work after the open issue queue was blocked: a shipped CLI without tests exposed a real validation defect (#1265), an entirely unused legacy inventory implementation was removed (#1267), and a persistence defect in the Wisk bootstrap path was found and repaired (#1270/#1271).

Wisk state has one canonical repository namespace: `.wisk/`. Versionable Experience, Wiki, Skill and local consumer knowledge belong beneath `.wisk/knowledge/`. During the package rename, #1270/#1271 temporarily used a tracked `.wisk -> .wikiskill` symlink to prevent state loss; #1274 later migrated the entire historical tree into `.wisk/` and removed the old namespace. The symlink is therefore useful migration evidence, not a current invariant and not a pattern to recreate.

Cross-session PR continuation should remain explicit through Wisk handoffs. A run that leaves CI or merge work pending records a Handoff; the continuing session first reconstructs the factual repository/GitHub state, then acts on the still-valid remainder and archives the Handoff only after resolution. A stale handoff instruction is never stronger evidence than the repository state observed on resume.

A green PR is not always immediately mergeable: GitHub can enforce a required status check (e.g. an app-provided "GitGuardian Security Checks" repository rule) that only reports against a head commit once something re-triggers it, independent of whether the repo's own CI workflow already passed on that same commit. Calling the merge API against such a PR fails with an HTTP 405 "Repository rule violations" naming the missing required check, even when `pull_request_read`'s own status view shows nothing blocking (a stale head can also leave the PR `mergeable_state: "behind"` its now-advanced base). The fix in both cases is the same action: update the PR branch (merge the current base into the head, e.g. via `update_pull_request_branch`), wait for the full required-check suite to report on the new head, then merge — do not conclude the PR is stuck or hand it back as an unresolved handoff without trying this first. This also matters when two independent loop rounds race on the same Handoff: one round's PR can sit open and merge-blocked for an extended period for exactly this reason, not because of any real conflict or review requirement, so a resuming round should check for and finish an already-open PR against a stale handoff rather than opening a duplicate.

A RunOutcome's `next_move` field is a legitimate work source in its own right, not just a courtesy note. Run 20260907T184502Z's outcome deferred two low-priority leads surfaced by an unrelated bugfix audit (a blind `except Exception` in `archive.py`, and `CircuitBreaker.is_open` reading a raw state field instead of its own class's dynamic `state` property). Run 20260907T192551Z investigated both with no new GitHub signal to go on (no owner-filed issue, no open PR, the 17-issue backlog still blocked): one was ruled out as already-correct (ruff's `BLE001` intentionally exempts handlers that call a `*.exception(...)` logger), the other was confirmed real and fixed with a dedicated RED→GREEN test (PR #1289, squash commit `b383135` — a sync-only caller reusing one long-lived `CircuitBreaker` across a whole run could never recover once it tripped open, because it only ever read the property that skipped the class's own time-based half-open promotion). When the issue backlog is exhausted and no handoff is pending, re-reading the most recent RunOutcome's `next_move` for an unresolved lead is cheaper and better-grounded than starting a fresh audit from scratch.

Three same-day bugs in `circuit_breaker.py` (`c352943`, `b383135`, and `#1293`) share one root cause worth naming as its own pattern: the class serves both a sync-only caller (`ia_s3.py`, which checks `is_open` then calls `record_success()`/`record_failure()` directly) and async callers (`archive.py`, `engine.py`, `drain.py`, which drive every state transition through `allow_request()`). Each bug involved a transition that one calling convention exercises and the other does not — `is_open` reading a stale raw field the async path never left stale (`b383135`), and `record_failure()`'s reopen-with-doubled-timeout branch only firing when `allow_request()` had already set `_probing` (`#1293`, found this round by re-reading the module against `ia_s3.py`'s actual usage rather than in isolation). A class shared between a sync and an async calling convention should be audited against *both* conventions explicitly, not just the async happy path that most of its tests exercise.

A fresh container checkout needs `wisk init .` before `wisk start` will select any SessionType. `.wisk/knowledge`'s managed bootstrap surface (`SessionType`/`RunSpec`/`CadencePolicy` records under `knowledge/system/`, plus `manifest.json` and `specs/`) is deliberately gitignored (`.wisk/.gitignore`) so it can be upgraded independently of the versioned consumer state (`experiences/`, `wiki/`, `skills/`, `local/`), but that means it does not exist at all right after a fresh `git clone` and `wisk start` fails with a bare `no-eligible-session`/empty `candidates: []` that gives no hint the fix is `wisk init .` (per `.claude/hourly-loop.md`). Two consecutive rounds (`20260907T222723Z`, `20260908T002654Z`) independently paid the full diagnosis cost for this in the same day; a future round hitting `no-eligible-session` with `candidates: []` should check for a missing `.wisk/knowledge/system/` directory first, before assuming the issue/handoff queue itself is exhausted.

`reset_manifest` (`src/djen_backup/service.py`, backing the `djen-backup reset` CLI command) is a second confirmed instance of a hazard worth naming on its own: a codebase that treats one field as the sole canonical status source (CLAUDE.md already states this for `djen_raw` vs. the derived `djen_status`, and `engine.py`'s check-priority builder enforces it at `engine.py:417-422`) must audit *every* function that clears or mutates the derived/mirrored fields, not just the ones an author happens to think of. `reset_manifest` cleared `ia_status`/`djen_status`/`updated_at` — exactly what its own docstring promised — but left `djen_raw` untouched, so `interpret_djen_raw()` re-derived the same terminal verdict the reset was supposed to clear, making the CLI command a silent no-op for exactly the entries an operator would run it against (fixed in PR #1297, squash `53cfe59`, with previously-zero test coverage for the function). The generalizable lesson: whenever a module names one field the canonical source of truth over a derived one, that invariant needs a positive test on every code path that resets/clears state, not just the read paths.

A shared domain exception needs auditing against every call site that can raise it, not just the one a change happens to touch — a distinct but structurally related hazard to the sync/async dual-calling-convention pattern above (both involve one abstraction with multiple independent consumers). `DJENRateLimitedError` is defined once, in `djen.py`, and raised by `get_caderno_url` for HTTP 403 (CloudFront/WAF block) — per CLAUDE.md's "never treat 403 as absent" rule, it exists precisely so callers treat a 403 as transient and retry rather than as a failure or an absence. `engine.py`'s `_classify_djen_status` and `probe.py` both already caught it explicitly. `drain.py`'s `_drain_one` (the newer batched upload-only drain mode) did not: its except clauses covered `DJENNotFoundError` and `(httpx.HTTPError, httpx.RequestError)`, but `DJENRateLimitedError` is a bare `Exception` subclass, not an `httpx` error, so a 403 propagated uncaught out of `_drain_one` and then out of `_drain_worker`'s `while True` loop, permanently killing that worker task for the rest of the run — exactly during the rate-limit bursts the exception exists to signal. Fixed with a RED (mocked 403, confirmed the exception propagated) → GREEN (added the missing `except` clause, matching the existing skip pattern) test in PR #1305. The generalizable check: when a module defines a domain exception for a shared client function, grep every call site of that function for a matching `except` clause before assuming an existing catch elsewhere means the exception is universally handled.

A human-facing architecture doc can drift from the codebase in the same way code itself can, and the failure mode is worse: it presents nonexistent files and functions as canonical guidance, not a stale claim about behavior. `FRONTEND.md`'s "Four tiers of state" (Tier 0) and "Dashboard queries with meta.json polling" sections documented `fetchAllData()`/`deriveData()`/`useDashboardWithPolling()` (the last from a `useDashboard.svelte.ts` file) and a `loadBuildTimeData()` helper (from a `buildTimeData.ts` file) as the current, working build-time-seed-plus-live-refresh architecture — complete with code samples attributed to real files (`[tribunal].astro`, `TribunalDetail.svelte`). Neither `useDashboard.svelte.ts` nor `buildTimeData.ts` exists anywhere in the repository (confirmed with `ls`/`grep`), and the two real files the samples were attributed to were independently verified to already use a different, current pattern (`loadContract()`/`readJson()` directly in `.astro` frontmatter, per CLAUDE.md's "Manifest query contracts"). The underlying `fetchAllData`/`deriveData` functions did still exist in `fetchData.ts` and type-checked cleanly, which is what let the doc's claim survive unnoticed — a stale reference to code that still compiles is much harder to catch by inspection than one that would fail to build. Fixed by deleting the dead exports (keeping `fetchWithRetry`, which is genuinely used) and rewriting every affected `FRONTEND.md` section with examples drawn from real, grep-verified call sites, landed as PR #1307. The generalizable check: before trusting or extending a claim in a project's own architecture doc — not just a wiki/knowledge entry about the loop itself — verify that every file and function it names actually exists and is called from where the doc says it is; a doc section can be "current" prose describing an abandoned or never-built subsystem for a long time before anyone reads it closely enough to check.

A completed design-system migration does not automatically erase every reference to the system it replaced -- it removes the system itself (the dependency, the import, the token definitions) but individual files that never got touched by the migration's own review can keep citing the old system's names indefinitely, especially if those files are also unreferenced dead code that nobody's tests or build would ever exercise. `web/src/components/TribunalCoverageGrid.astro` had zero importers anywhere in the repository (the same category of bug as PR #1300's `TribunalCalendar.svelte`), and its one piece of real styling was `background: var(--pico-muted-border-color))` -- a Pico CSS custom property. CLAUDE.md's CSS token boundary section already documents that Pico CSS was fully replaced by Panda CSS/the `cobogo` preset (#1169) and that `--pico-*`/`--tinta-*` variables "no longer exist anywhere in the codebase"; that claim itself was almost invalidated by this one file, since the variable was never defined in `index.css` and would have silently resolved to nothing had the component ever been wired up. Fixed by deletion (PR #1309, squash `4a77670`), verified by full web suite/typecheck/lint/build green before and after plus a repo-wide grep for the component name returning nothing. The larger, still-open instance of this same pattern: `FRONTEND.md`'s "Tech Stack Overview" table still lists "Pico CSS (semantic baseline) + Vanilla CSS with design tokens" as the Styling row, and the document's entire dedicated "Pico CSS — Semantic HTML as the First Styling Layer" section (~70 lines of patterns and anti-patterns) presents Pico as current, canonical guidance -- a bigger doc-drift fix than any single dead file, deliberately deferred to a future round rather than rushed alongside this one.

`FRONTEND.md` has now been wrong about a different area in three consecutive rounds within the same session, which is strong enough signal to name as its own observation about this specific file's reliability rather than three unrelated coincidences: PR #1307 found the "Four tiers of state" architecture section documenting nonexistent files (`useDashboard.svelte.ts`, `buildTimeData.ts`) as canonical; PR #1309 found a single dead `--pico-muted-border-color` reference in an orphaned component; PR #1311 found the entire dedicated "Pico CSS" section plus its "Theming" subsection stale -- Pico's semantic-HTML-styled-for-free model no longer describes how styling works (confirmed by reading `node_modules/cobogo/preset/index.mjs` directly: `globalCss` covers only `html`/`body`/`::selection`/`a`), and the light/dark theme toggle it described was deliberately removed in issue #1178, guarded by a dedicated regression test (`themeSingleModeGuard.test.ts`) that already exists specifically to keep it from reappearing. In each case the stale prose survived because the code it referenced either still compiled (PR #1307) or was simply never exercised by tests or a build (PR #1309, and `FRONTEND.md` itself is never checked by any build step). The generalizable lesson beyond "verify claims before trusting them" (already recorded above): a project's own hand-maintained architecture doc drifts fastest in exactly the areas a migration doesn't force a compile error to reveal -- a completed migration (Cobogo/Panda replacing Pico, #1169; the single-theme decision, #1178) removes the *implementation* cleanly but has no mechanism to touch prose describing the *old* implementation, so treat any doc section describing a system's "current" implementation as a candidate for staleness precisely when that system has had a recent, deliberate migration away from something, whether or not the doc has been flagged yet.

A one-off ops script that duplicates a shared client's classification logic instead of importing it will drift the moment the shared logic is fixed and the script is not. `scripts/drain_unknowns.py` is an ops workaround (see its own module docstring: "runs via the drain-unknowns workflow while the engine timeout is unresolved") that reimplements `engine.py`'s `_classify_djen_status` as a local `_classify` function instead of calling it, because the two have different call signatures (no `AsyncLimiter`, a bare `httpx.AsyncClient` instead of the engine's wrapped client). When engine.py was fixed to special-case `DJENNotFoundError(status_code=200)` -- DJEN's "Sem comunicações" response -- into the `"no_publications"` absent sentinel (per CLAUDE.md's explicit warning about the historical ~79K-row false-`available` bug), that fix was never mirrored into the copy in `drain_unknowns.py`, which kept returning the bare `"200"` and so kept reintroducing the exact bug on every run of the live scheduled `drain-unknowns.yml` workflow. Found by grepping every caller of a DJEN-classifying function rather than assuming the one properly-tested call site (`engine.py`, covered by `tests/djen_backup/test_classify_djen.py`) was the only one; fixed with a mirrored RED (`tests/test_drain_unknowns_classify.py`, 6 cases copying the engine test's coverage) -> GREEN test, landed as PR #1315 (squash commit `a00561f`), merged with 9/9 checks green and no review comments. The generalizable check, alongside the shared-domain-exception and sync/async dual-caller patterns already recorded here: when a module's own docstring or history explains that it duplicates another module's logic for structural reasons (different signature, different caller shape), grep for other reimplementations of the same classification/decision logic before trusting that a bug fixed in the "main" implementation is fixed everywhere it matters.

A second, independent instance of that exact duplicated-classification-logic pattern: `src/djen_backup/manifest.py`'s `SyncManifest._normalize_event` and `scripts/render_manifest_parquet.py`'s `_normalize_manifest` both hand-implement CLAUDE.md's two-rule "absent self-consistency" invariant (absent+bare-200 raw → `no_publications` sentinel; absent+empty raw → downgrade to unknown) once in Python, once in DuckDB SQL, for the same structural reason as `drain_unknowns.py`/`engine.py` (different runtime shape — one is the live in-memory engine, the other a offline batch compactor). Unlike `drain_unknowns.py`, this pair had not yet drifted on the rule that already existed (the 200-sentinel rewrite, both correct and both tested) — but the *second* rule (empty-raw downgrade) had only ever been added to the Python copy, never to the SQL copy, so the compactor could silently persist exactly the state CLAUDE.md says must never survive a compaction. Found the same way as the `drain_unknowns.py` case: a background Explore-agent audit grepped every implementation of the absent-self-consistency rule rather than trusting the one with an existing test. Fixed with a mirrored RED (`tests/test_render_manifest_compaction.py::test_normalize_manifest_downgrades_absent_with_empty_raw_to_unknown`) → GREEN test, landed as PR #1323. Not yet extracted into one shared source of truth — deliberately deferred as this round's `next_move`, since the two copies are consistent again after this fix and premature extraction across a Python/DuckDB-SQL boundary has its own cost.

A `next_move` deferral that says "premature extraction... has its own cost" is a note about timing, not a standing veto — a second round is the point where the deferral pays off, once the pattern is confirmed rather than speculative. Run 20260908T112621Z deferred extracting the absent self-consistency rule (shared by `manifest.py`'s `_normalize_event` and `render_manifest_parquet.py`'s `_normalize_manifest`) because "the two copies are consistent again... premature extraction across a Python/DuckDB-SQL boundary has its own cost". By the time this round picked it up, the pair had already drifted and been caught twice on the same rule family (PR #1315's `drain_unknowns.py`/`engine.py` instance, then PR #1323's own empty-raw-downgrade gap) — two independent confirmations that "structurally forced to duplicate, no shared source of truth" reliably drifts again, which is what made the extraction worth doing now rather than still deferring it a third time. The concrete shape that respects the Python/DuckDB-SQL boundary: a shared module (`src/djen_backup/absent_consistency.py`) holding the rule's constants and a pure Python function (`normalize_absent`) as the single source of truth; the in-memory engine (`manifest.py`) calls the function directly, while the bulk-SQL compactor (`render_manifest_parquet.py`) can't call it per-row without losing its `UPDATE`'s bulk-set performance, so it instead builds its SQL literals by interpolating the same constants — removing the duplicated *definition* (magic strings, rewrite order) while keeping each runtime's own call site. A fixture-driven parametrized test (`tests/test_absent_consistency_shared.py::test_sql_normalization_agrees_with_python_rule`) then asserts the SQL path and the Python path agree on the same representative rows, so a future edit to only one side fails CI immediately rather than silently reintroducing the drift a third time. Landed as PR #1325.

A fifth confirmed-dead-code instance, and the sharpest example yet that a `next_move` lead can be *disproven* rather than merely fixed. Run `20260908T152704Z`'s `next_move` flagged `web/src/lib/coverageInsights.ts`'s `buildCatalogAttentionCards` -- its `'recent-drop'`/`'persistent-absence'` heuristics walk days by calendar date, not business date, a plausible bug -- but explicitly deferred acting on it: "this function may be part of the already-flagged ~55% dead code in the same file with zero call sites... worth a live-caller trace before acting on it". Run `20260908T162521Z` did that trace: a repo-wide grep showed the only two importers of the module (`TribunalDetail.svelte` and the module's own test file) use exclusively the sibling `buildTribunalAttentionCards`, and none of `buildCatalogAttentionCards`, `summarizeCatalogDay`, `filterCoverageDays`, `countCoverageFilters`, `getDayStatusLabel`, or their three supporting types had a single caller anywhere. The calendar-day bug was real but permanently unreachable, so the correct action was deletion, not repair -- fixing a bug in code nothing calls would have delivered zero product value while leaving the actual dead-code hazard in place. Landed as PR #1332 (squash commit `e22b818`), with a module-surface regression-guard test (`expect(Object.keys(coverageInsights).sort()).toEqual(['buildTribunalAttentionCards'])`) added specifically so the same dead surface can't silently reappear the way `TribunalCoverageGrid.astro`'s `--pico-*` reference or the `.auto-grid` CSS did. The generalizable lesson, sharpening the existing "verify dead code via grep before repair vs. removal" pattern: when a `next_move` lead already names "might be dead code" as the reason it wasn't acted on, resolving that uncertainty (not the originally-flagged bug) is the round's actual task -- the trace's answer, not the bug's fix, determines what ships.

A Wisk CLI usage gotcha worth recording so a future round doesn't re-diagnose it: `wisk run check <run> <component-id> handoff-disposition ... <result> <status>` parses the accepted/reframed/rejected disposition by taking the `result` string, lowercasing it, and splitting on the first `:` and then on whitespace -- so the disposition keyword must be the literal first token of `result`, e.g. `"accepted: <rationale>"`, not a labelled prefix like `"Disposition: accepted: <rationale>"` (which parses to the token `"disposition"`, not `"accepted"`, and the check silently fails structural validation with `observed: "disposition"` rather than raising an argument error). The CLI also has no update/overwrite for an already-recorded component: a second attempt at the same `component-id` raises `FileExistsError`, so recovering from a bad first attempt means deleting the wrongly-written `.md` file under `.wisk/knowledge/experiences/runs/` before re-recording.

A sixth confirmed instance of the duplicated-DJEN-classification-drifts pattern (circuit_breaker.py x3, `drain_unknowns.py`/`engine.py`, `manifest.py`/`render_manifest_parquet.py` x2), and the first found in an ops/diagnostic script rather than a production code path. `scripts/backfill_probe.py`'s whole stated purpose (its own module docstring) is to spot drift between the manifest's recorded `djen_raw` and what DJEN returns live right now -- but its `_probe_one` derived `live_raw` purely from the bare HTTP status code (`str(resp.status_code)`), never inspecting the JSON body, so a genuinely-absent live probe (HTTP 200, body `{"status": "Sem comunicações"}`, no download URL) was reported as `live_raw="200"` and classified "available". This is exactly the historical ~79K-row false-available bug CLAUDE.md documents, reproduced inside the one tool whose job is to catch that class of drift -- every *other* DJEN caller in the codebase (`engine.py`'s checker, `djen_backup/probe.py`'s own `_probe_one`, `scripts/drain_unknowns.py`) already derives its raw code from `get_caderno_url`, which raises `DJENNotFoundError(status_code=200, ...)` specifically for this case. Fixed with a RED (`tests/test_backfill_probe_live_classify.py`, new file -- asserted `live_raw=="no_publications"`, got `"200"` against the old code) -> GREEN (`_probe_one` now calls `get_caderno_url` directly plus `segments.absent_raw_code`, the same helper `djen_backup/probe.py` already uses, for the `DJENNotFoundError` branch) test, landed as PR #1334 (squash commit `07e2b047`). A near-miss worth naming on its own: the first attempt at writing the RED test used the Write tool on a path that already existed (`tests/test_backfill_probe_classify.py`, an unrelated, still-valid test suite for the sibling `_classify` manifest-raw-to-category mapper) and would have silently deleted that coverage; caught via `git diff` before committing, the original was restored and the new tests placed in their own file (`tests/test_backfill_probe_live_classify.py`) instead. The generalizable check, sharpening the existing pattern once more: an ops/diagnostic script that duplicates a shared client's classification logic is exactly as prone to drift as a second production code path, and no less worth auditing -- "it's just a debug tool" is not a reason to skip the grep-every-call-site check.

A seventh distinct root-cause family, found in the same sweep that cleared `src/causaganha_mcp` entirely and left `src/datajud`/`src/causaganha/decisoes`/`src/causaganha/processos` substantially clean: a summary/count field a caller relies on for user-facing text must be derived from what a function *actually executed*, not from a static plan describing what it *intended* to do before runtime branching could skip part of it. `causaganha/decisoes/search.py`'s `search_decisions` computed `datasets_consultados=plan.total_datasets` (`len(plan.juris) + len(plan.stj) + len(plan.tcu)`, a property on the immutable `DecisionSearchPlan` built before the query loop ever runs) — but the same function's own loop explicitly `continue`s past the STJ source whenever a `cnj` or `orgao` filter is present, because STJ's `numeroProcesso` is never the source CNJ (#1045) and STJ exposes no verified órgão colegiado (#1064), making an STJ match structurally impossible in both cases. So a cnj- or orgao-filtered call correctly skipped querying STJ and correctly added a `limitacoes` entry saying so, while still reporting a dataset count that included the unqueried source — the MCP tool `decisoes_buscar`'s `resumo` string then told an agent "N resultado(s) em M dataset(s)" where M counted a dataset the same response's own limitations text said was excluded. Unlike the DJEN-classification-drift family (a *value* computed wrong from a *live* signal), this is a *reporting* bug: the underlying search behavior was already correct, only the metadata describing what happened lagged behind an intentional skip a later commit introduced without updating the field that summarizes execution. Fixed by accumulating the count field inside the loop itself (`datasets_consultados += len(datasets)`, only reached for sources not skipped) rather than from the pre-computed plan property, with RED assertions added to both pre-existing skip-tests. Landed as PR #1340 (squash commit `b85fcf8`). The generalizable check, distinct from the existing six: whenever a function's return value includes a count/summary field alongside a `limitations`/`warnings`-style field describing partial execution, verify the count is computed from the same runtime branching as the limitation, not from an earlier, static plan — a "here's what we *planned* to touch" number silently drifts from "here's what we *did* touch" the moment any conditional skip is added to the execution path without a matching edit to the summary field.

An eighth distinct root-cause family, and the most severe import-time instance found so far: a CLI framework call with a subtly wrong argument order can crash a whole module at *definition* time, and nothing catches it if no test ever imports that module. `src/causaganha/consolidate/cli.py`'s `reconsolidate()` declared `force: bool = typer.Option("--force", default=False, help=...)` — passing the option's own name string positionally into Typer's `Option(default, *param_decls, ...)` signature (an older, still-accepted calling convention) while *also* passing `default=False` as a keyword, which Typer's `Option()` rejects with `TypeError: Option() got multiple values for argument 'default'` the moment the module's class body executes. Because Python evaluates function-signature defaults at *def* time, this is not a runtime bug reachable only via a specific code path — it makes `import causaganha.consolidate.cli` itself raise, so every subcommand in the file (`date`, `tribunal-year`, `backfill`, `reconsolidate`) was unusable via `python -m causaganha.consolidate ...`, and had apparently been so for some time (the line predates this round's own diff, confirmed via `git blame`). It escaped detection specifically because `tests/consolidate/` had zero files that imported `cli.py` at all — this repository's four Cyclopts-migrated CLIs (`djen_backup`, `tjro_juris`, `stj_acordaos`, `datajud`, per RFC 0013) each have `tests/cli_contract/` coverage that imports and invokes their `app`, but `consolidate/cli.py` was explicitly out of that RFC's scope and had never gained an equivalent smoke test. Fixed by correcting the argument order (`typer.Option(False, "--force", help=...)`, matching every other option in the same file) and adding `tests/consolidate/test_cli_importable.py` — three cases: the module imports, and two representative subcommands' `--help` build and exit 0 — landed as PR #1350 (squash commit `ed0973c`). The generalizable check, distinct from the seven above: any CLI/service module that no test ever imports is a module whose *definition-time* correctness (decorator/`Option`/`Parameter` calls, class bodies, top-level code) is completely unverified regardless of how much its runtime logic is tested elsewhere — a bare "does this module import" test is cheap insurance precisely because Python raises exactly these errors before any of a module's own tests could ever run.

A ninth pattern, found in the same audit and only reachable once the eighth was fixed (its own module couldn't be imported before that): a readiness/completeness gate must be checked against what a given code path can actually produce, not against a metric that path structurally can never reach. `consolidate/cli.py`'s `_uploads_complete()` gated writing consolidation stats to the manifest on `stats["uploaded"] == len(non_empty_tables)` — correct for a real upload run, but `--dry-run` mode's own upload loop deliberately never increments `stats["uploaded"]` (nothing is actually uploaded, by design), so for any dry run with real, non-empty data the gate's left-hand side was permanently `0` while the right-hand side was `>0`, and the gate could never pass. This silently defeated the exact behavior the surrounding code's own comment promised ("For dry runs, we don't upload but we can still register stats of non-empty tables to manifest") — a documented intent with an unreachable implementation, and zero test coverage to catch the gap. Fixed by giving `_uploads_complete()` a `dry_run` parameter: in dry-run mode, completeness means "every non-empty table exported without failure" (`stats["export_failures"] == 0`), never an upload count that mode cannot produce. RED test (`tests/consolidate/test_cli_dry_run_manifest.py`) built a real DuckDB table, ran the real `_export_upload_and_manifest` end-to-end (only `update_consolidation_manifest` mocked as a spy) with `dry_run=True`, and confirmed the manifest call never fired before the fix, did after; landed in the same PR #1350. The generalizable check: whenever a function has a "skip the real side effect" mode (dry-run, preview, simulation), any downstream gate that reads a counter the side effect normally increments needs its own explicit branch for that mode — silently reusing the same gate assumes the counter still means the same thing, and it doesn't.

A tenth pattern, this one about audit *tooling* itself rather than the code the audits check. `scripts/segmenter_semantic_audit.py`'s `find_anti_patterns` iterated every `AnnotationRecord` a document ever had, including ones already superseded by a later, corrected one — so once a flagged document was repaired via a new, later-`completed_at` annotation (the store's immutable, append-only design: a correction is always a new record, never an in-place edit), the audit kept reporting the exact same finding against the old, no-longer-used record forever. This made the script self-defeating as a repair-completion signal: there was no way for a fix to ever make it go quiet. The fix mirrors `release.py`'s own `_latest_annotation` (the function that actually decides which annotation a training release consumes, RFC 0012 §10) — an audit of "the effective current state" must select records the same way the real consumer does, not sweep every record that was ever written. An eleventh root-cause family, and a sharper instance of the "invariant stated in a docstring but never enforced" hazard than any recorded so far: the docstring can point at a *specific named function for the enforcement*, and that function can simply not exist. `schemas.py`'s `AnnotationRecord.is_independent_capable()` checks the per-record necessary condition for RFC 0012 §5.3's annotator-independence definition (`seeded_with == "none"`) and its own docstring explicitly defers the pairwise half -- "distinct model families... which is a property of two records together, not one" -- to `segmenter_dataset.mechanical.annotations_are_independent`. That function did not exist anywhere in the repository (confirmed by grep across `src/` and `tests/`), and `is_independent_capable()` itself had zero callers. Worse, the one real enforcement site that *did* have both annotations in hand -- `release.py`'s `_iaa_gates`, which resolves a review's `input_annotation_ids` back to `AnnotationRecord`s to compute inter-annotator agreement -- only checked `len(inputs) >= MIN_INDEPENDENT_ANNOTATIONS_FOR_IAA`, never independence. Concretely: a review built from an annotation and a second annotation seeded from the first's own output (a "correction pass over a model draft", which RFC 0012 §9 names explicitly as *not* independent) would compute a near-1.0 IAA and pass the rigid, non-waivable `iaa_aggregate_floor` gate -- fabricating exactly the inter-annotator reliability evidence that gate exists to certify, with nothing in the pipeline able to catch it. Found by a dispatched Explore-agent audit of `segmenter_dataset` modules not yet covered by prior rounds (continuing #1050), independently re-verified line-by-line before acting (grepping every call site of the missing function name, then reading `_iaa_gates`'s pair-selection loop directly). The generalizable check, sharpening the existing "verify a docstring's claim before trusting it" pattern: when a docstring defers part of an invariant to a named function in another module, don't just check that function exists -- grep every call site that has access to the data the invariant is *about* (here, any place holding two `AnnotationRecord`s together) and confirm at least one of them actually calls it, because a docstring cross-reference to a nonexistent function is invisible to every tool that doesn't try to import it. Deliberately left unfixed and named as this round's own `next_move`: `ReviewRecord._at_least_two_inputs_when_accepted` still only checks the count of `input_annotation_ids`, not the referenced annotations' independence, so a non-independent-pair review can still be *written* and accepted -- today's fix only stops it from being *used* as IAA evidence at release time; and `gates.py`'s `no_unresolved_annotation_conflicts` gate is hardcoded `passed=True`, never checking anything.

A twelfth pattern, resolving the first of the two concrete gaps PR #1373's own `next_move` named rather than opening a new audit. RFC 0012 §14 lists "nenhum conflito de anotação não resolvido" as its own rigid, non-waivable gate -- textually and structurally distinct from `val_test_independently_adjudicated` (which only checks that a val/test document *has* an accepted review at all, never that a disagreement elsewhere was actually looked at). `release.py`'s `no_unresolved_annotation_conflicts` `GateResult` was `passed=True`, hardcoded, with the comment "resolved by latest accepted review per document" -- a claim about how `resolve_split` behaves, not a check that it was true. Concretely: `resolve_split`'s train role always picks `_latest_annotation` (latest `completed_at` wins) with no reference to review state at all, so a document with two disagreeing `AnnotationRecord`s and zero reviews would silently use the newer one's labels with no record the older annotator's conflicting labels were ever adjudicated. Fixed by adding `_unresolved_conflicts(annotations, reviews)`: groups `AnnotationRecord`s by `document_id`, compares every pair's `labels` for disagreement (`frozenset(labels)` equality -- `Label` is a frozen Pydantic model, so this is order-independent unlike a bare list-equality check), and treats a disagreeing pair as resolved only if an accepted `ReviewRecord`'s `input_annotation_ids` is a superset of both `annotation_id`s (not exact-set-equal, since RFC 0012 §8 already allows more than two inputs per review). RED test built exactly this fixture (two annotations on one train document, differing only in `cabecalho_fim`'s end offset, both individually mechanically valid so the failure couldn't be confused with `ontology_schema_valid`) and confirmed the old gate let it through; GREEN after the fix, plus a second assertion in the same test that adding a covering accepted review lets the release succeed -- proving the gate isn't just failing-open in the other direction. Landed as PR #1375. The generalizable check, sharpening the "hardcoded no-op gate" hazard the eleventh pattern already named for a different gate in the same file: when a rigid gate's `GateResult` literal is a bare `True`/`False` with no computation behind it, grep the RFC section that defines it for language distinguishing it from its structural neighbors (here, "any unresolved conflict" vs. "every val/test record adjudicated") before assuming an adjacent, already-implemented gate covers the same ground.

A thirteenth pattern, closing the second and final concrete gap PR #1373's own `next_move` named (the first, `no_unresolved_annotation_conflicts`, was closed by the twelfth pattern/PR #1375 above). RFC 0012 §9 requires an accepted review to certify two *independent* annotations, but `ReviewRecord`'s own pydantic `model_validator` (`_at_least_two_inputs_when_accepted`) can only check the *count* of `input_annotation_ids` -- a frozen pydantic model has no access to the annotation store, so it cannot resolve those IDs back to `AnnotationRecord`s and check `mechanical.annotations_are_independent`. `release.py`'s `_iaa_gates` already ran that exact check, but only at release time, to exclude a non-independent pair from IAA evidence -- nothing stopped `SegmenterDatasetStore.write_review` from persisting such a pair as `"accepted"` in the first place, which is the state RFC 0012 §9 says shouldn't exist at all. Two pre-existing `test_release.py` fixtures had incidentally relied on writing a non-independent-pair accepted review as setup for unrelated release-gate assertions -- one was trivially fixed (its two annotators just needed distinct `model_family` values, unrelated to what it was actually testing), but the other's entire premise (proving `_iaa_gates` excludes a non-independent pair that *did* get written and accepted) became unreachable through the public API by this same fix. The generalizable lesson, sharpening the "hardcoded no-op gate"/"invariant checked too late" hazards named above: when an invariant is enforced only at the *consumer* of some data (here, `_iaa_gates` at release time) rather than at the data's *write* site, the write site can still produce and persist exactly the invalid state the invariant exists to rule out -- worth checking, for any validated-late invariant, whether the earlier write path can be given the same check instead of only ever filtering after the fact.

A fourteenth pattern, and the first found by a background Explore-agent audit dispatched specifically to sweep `web/src/lib` modules not yet covered by any prior round's own module list. `web/src/lib/velocityCalc.ts`'s `calculateVelocityAndRegression` runs two separate day-walk loops over the same `coverageSet`: the historical/current-30-day/baseline-60-day loop filters every day through `isBusinessDayIso` before counting it, but the `weeklyData` loop (whose sum feeds `currentVelocity`, the number behind the public dashboard's "Acelerando"/"Desacelerando" trend badge) did not. The generalizable check, distinct from the existing doc-drift and duplicated-classification-logic families: when an invariant is asserted as fact in more than one place that each independently *consume* it (not just describe it, the way a prose doc describes a system), grep for the one place that *produces* the data the invariant is about (here, every write path that can add to the manifest, including a pruning/cleanup function's own carve-out) before trusting that "can never happen" is still true everywhere it's repeated -- two consumers of the same false invariant can diverge from each other silently, with no compile error and no single obviously-stale doc section to catch it.

A fifteenth pattern, and the first found in `scripts/render_queries.py` (the `.qmd` → JSON query-contract renderer CLAUDE.md's "Manifest query contracts" section documents): an error-isolation boundary built to contain one failing unit of a batch, scoped to only one exception type raised by that unit's own call, silently fails to contain a *different* exception type the same call can raise -- and the whole batch goes down with it. `render_all()`'s per-contract loop wraps `run_query(con, sql, fmt)` in `try/except duckdb.CatalogException`, correctly isolating the "missing view/table" case (an `optional` contract's data source not yet registered) so one bad contract can't take down the others. But `run_query()` itself also raises a bare `ValueError` when a `format: object` contract's SQL returns anything other than exactly one row -- a real, common contract-authoring bug, not a missing-source case -- and that exception type was never in the `except` clause. The result: a single misbehaving `format: object` contract crashed `render_all()`/`main()` entirely, silently skipping every `.qmd` file that sorts after it (files are processed in sorted-filename order) with zero per-file failure reported for any of them. Worse, `--check` (`check_queries()`) provided no safety net, because it executes each contract's SQL directly and never calls `run_query()` at all -- so it never exercises the `format: object` single-row invariant, meaning a PR could pass `--check` clean and still crash `deploy-web.yml`'s `--strict` render step (and `update-catalog.yml`'s non-strict one) in production. Found by a dispatched Explore-agent audit of previously-unswept modules (continuing the pattern from run `20260909T164153Z`'s own `next_move`), verified with a live repro (two synthetic `.qmd` files, confirmed the second, unrelated, alphabetically-later one never rendered). Fixed with RED (`test_render_object_format_row_count_violation_is_failure_not_crash`, confirmed the uncaught `ValueError` before the fix) → GREEN (added `except (ValueError, duckdb.Error)` alongside the existing `CatalogException` branch, always recording the contract as a required failure -- a query bug is not the "missing optional source" case `CatalogException` already handles for `optional: true` -- and continuing to the next `.qmd`), landed as PR #1389 (squash commit `e84f67d`), merged with CI green and zero reviews/comments. The generalizable check, distinct from the fourteen patterns above: when a loop's `try/except` exists specifically to isolate one iteration's failure from the rest of a batch, grep every exception type the wrapped call can actually raise (not just the one the original author happened to test against), because a narrower-than-intended catch clause silently reintroduces the exact batch-wide failure the isolation boundary was built to prevent.

A sixteenth pattern, sharpening the fourteenth (`velocityCalc.ts`'s two divergent day-walk loops) for a different artifact type: two `.qmd` query contracts that each independently compute a per-bucket aggregate over the *same* manifest concept -- "is this day settled enough to count toward a summary statistic" -- can drift from each other exactly like two consumer loops in one function can, because nothing forces the second file to inherit a fix made to the first. `stats_coverage.qmd`'s `best_day`/`worst_day`/`best_count`/`worst_count` were fixed (this session's own immediately preceding round) to exclude a still-`pending_real` day from best/worst selection via a `raw_absent`/`unsettled` classification CTE. `weekly_pattern.qmd` computes a structurally identical aggregate -- average coverage, this time bucketed by day-of-week instead of a 30-day window -- over the same `manifest` table, but had no such classification at all, so a weekday whose only recent occurrence was still in flight had its historical average silently diluted downward, exactly the failure mode the sibling file was already fixed for. The generalizable check, distinct from the fourteenth pattern's single-function scope: when one `.qmd` contract gets a settled/unsettled (or any other correctness) fix, grep every other `.qmd` file computing an aggregate over the same source table for the same unstated assumption -- a fix to one consumer of a shared concept does not propagate to a sibling consumer of the same concept just because they live in separate files with separate tests.

## Context & Scope

These rules apply to unattended or periodically invoked CausaGanha work sessions. They do not authorize speculative features when current issues are blocked, nor do they turn coverage/dead-code scans into a mandatory ritual. They describe a proven fallback: prefer independently verifiable repository improvements over manufacturing work merely to keep the loop busy.

The issue backlog remains important context, but it is a queue of known opportunities rather than a completeness claim about all possible useful work. Before acting on cached blocker descriptions, refresh the relevant GitHub/environment facts when staleness could change the decision.
